## Phase 1 — The subprocess runner cannot lie or hang (two days)

All four findings live in `bench/process.rs` and share one root cause: the runner has three independent clocks (stdin write, stdout read, stderr thread) and one non-blocking exit probe. Fix them as one design change, then the individual symptoms go away.

### 1.1 One deadline per case

**Finding**: `process.rs:129` writes the request with a blocking `write_all` and no deadline. A live adapter that stops draining stdin, given a request over the 64 KiB pipe buffer, hangs the run forever. `case_timeout_ms` only guards the read at line 137.

**Change**: compute `deadline = Instant::now() + case_timeout_ms` once at the top of `execute`. Move the stdin write onto the existing writer path so the main thread never blocks: either a dedicated writer thread fed by a channel, or non-blocking stdin with `poll` under the same deadline. Every subsequent `recv_timeout` uses `deadline.saturating_duration_since(now)`, not a fresh `case_timeout_ms`.

**Test**: add fixture mode `hang-before-read` that sleeps without reading stdin. Send a 200 KiB candidate with `case_timeout_ms = 250`. Assert the row is `Timeout`, the next case is recorded, and the test completes within five seconds even under concurrent CI load rather than waiting for the fixture's 60-second sleep.

### 1.2 Stderr is process-level telemetry, not per-case evidence

**Finding**: `process.rs:158` snapshots the `Arc<Mutex<StderrCapture>>` when the stdout line arrives, with no synchronisation against the stderr thread. Overflow classification and `stderr_sha256` are timing-dependent; line 128 resets the buffer unconditionally, so late stderr from case N is charged to case N+1 and stderr between cases is dropped.

**Why timing cannot fix it**: no parent-side sequence number can tell which case produced a byte the child wrote late. Any attribution by arrival time stays nondeterministic, and the bench's compare step would keep reporting phantom drift.

**Change**: stop attributing stderr to cases. Capture it once per child process as process-level telemetry: total bytes, overflow flag, digest, and the retained prefix, recorded on the run manifest per (system, spawn). The per-case row keeps only the identity-bound JSON response, which is the one artifact the adapter itself ties to a `request_id`. Anything an adapter wants attributed to a case goes in the response's `diagnostics` field, which the protocol already carries. `max_stderr_bytes` overflow becomes a process-level failure that terminates the child and marks the in-flight case `InvalidOutput`; later cases proceed under a fresh spawn within the restart budget.

**Test**: fixture mode `stderr-burst` writes `max_stderr_bytes + 1` to stderr then the result line with no sleep. Run 20 repetitions. Assert `compare` between any two runs reports zero drift in coverage states and row digests. Remove the 10 ms sleep at `please-eval-bench-fixture.rs:85`; the harness must not depend on it.

### 1.3 Exit status comes from the reap, not a probe

**Finding**: `process.rs:183` uses `try_wait()` right after stdout EOF. The kernel closes fds before the child is reapable, so a non-zero exit reads as `None` and the row is `InvalidOutput` instead of `Crashed`. Measured at roughly 8% under load; this is the flaky `process_failures_remain_rows_and_later_cases_continue`.

**Change**: on `Eof`, call `terminate_state` first and use the status it returns, as the `Timeout` path at line 139 already does through `terminate_capture`. Delete the `try_wait` probe and the `let _ =` discard.

**Test**: fixture mode `crash` with `exit(17)`. Run 50 repetitions under `--test-threads=8` with the workspace build running concurrently. Assert 50 of 50 rows are `Crashed` with `exit_status = Some(17)`.

### 1.4 Telemetry excludes runner overhead

**Finding**: `process.rs:275` measures `elapsed` after the unconditional 2 ms duplicate sniff at line 250, inflating every subprocess row by at least 2000 µs and costing N × R × 2 ms per system.

**Change**: snapshot `elapsed` immediately after the result line is received, before the sniff. Keep the sniff, since removing it races the reader thread, but record its cost separately as `telemetry.runner_overhead_micros`.

**Test**: not a wall-clock threshold; those fail under CI and WSL load. Inject a clock (a `Fn() -> Instant` on the runner, monotonic counter in tests) and assert the response timestamp is captured before the duplicate-response check begins, i.e. `elapsed` excludes the sniff by construction. Assert `runner_overhead_micros` is present and non-negative.

### 1.5 Handshake failures terminate the child

**Finding**: `process.rs:313` and `:328` return with `?` before `terminate_state`; the child leaks and becomes a zombie once it exits on stdin EOF. Restart budget is uncapped by `validate_limits`, so the leak count is unbounded.

**Change**: wrap the handshake body in a closure; on any `Err`, terminate and reap before propagating. Cap the budget at 100 in `validate_limits`.

The comparison at line 95 (`starts > restart_budget`) is correct if the field means restarts after the initial start, and it is wrong if it means total starts. The schema says neither. Rename the field to `max_restarts` in the experiment schema and `RunLimits`, keep the current comparison, and state the meaning in BENCH.md. Do not change the arithmetic.

**Test**: fixture mode `bad-handshake` prints `{garbage`. Assert the run reports startup failure and `ps --ppid <runner>` shows no surviving children.

### 1.6 Do not kill a reaped pid

**Finding**: `process.rs:487` calls `libc::kill(-pid, SIGKILL)` unconditionally; if the child was already reaped and the pid recycled, an unrelated process group is killed.

**Change**: `terminate_state` checks `try_wait()` first and skips the raw kill when the child has already exited. After 1.3 this is the only remaining path that can reach a reaped child.

**Test**: unit test on `terminate_state` with a child that has already exited and been waited; assert no `kill` syscall is issued (wrap the libc call in a small trait so the test can observe it).

## Phase 2 — The bench measures what PLEASE actually does (one day)

### 2.1 Incomplete does not overrule detected

**Finding**: `please.rs:99` labels any verdict with a non-empty `incomplete()` as `indeterminate` and `CoverageState::Unavailable`, even when `ScanDecision::from_verdict` already returned `AtOrAboveThreshold`. The report then counts a case the shipped CLI blocks as a false negative plus an unavailable failure.

**Change**: order the decision the way `crates/scan/src/lib.rs:27-34` does. `detected` wins; only downgrade to `indeterminate` when `detected` is false and `incomplete` is non-empty. Keep the incomplete causes in `diagnostics` either way.

**Test**: a case with 17 hits of one rule (past `DEFAULT_MAX_MATCHES_PER_RULE = 16`). Assert `label = "detected"`, `coverage = Completed`, `diagnostics` contains `max_matches_per_rule`.

### 2.2 Tier metadata records what was requested

**Finding**: `please.rs:50-56` hardcodes `{"structural":true,"ml":false,"judge":false}` and emits a metadata shape different from `product.rs`. FR-721 is nominally satisfied by a constant.

**Change, two steps**:

- **2.2a (this plan)**: build a `product::Runtime` from the system manifest for the structural product and mechanism modes the manifest can already express, and call `Runtime::session` and `Runtime::metadata`. Delete the re-derivation in `PleaseAdapter::new`. The tier block in the metadata then reflects the runtime, which for today's manifests is structural only. This is architecture candidate 2.
- **2.2b (follow-on, not in this plan)**: ML and judge tiers need manifest fields the bench contract does not have (model path, judge credentials policy, network permission interacting with `network_capable`). That is a contract expansion with its own schema bump and spec text. Record it as a deferred item; do not present 2.2a as delivering it.

**Test**: system manifest with `mode: product`; assert the recorded metadata equals `product::Runtime::metadata()` byte for byte, and that the tier block is derived rather than a literal.

### 2.3 Pack check is order-independent

**Finding**: `pack.rs:240` inserts every case's kind-tagged label into `labels_by_digest` but only compares artifact cases against it. A contextual case sharing bytes with an artifact case makes verification depend on case order. Reproduced by moving `user-01-artifact` after its siblings.

**Change**: key `labels_by_digest` on `(asset_sha256, surface)`, or insert only when `surface == ArtifactDetection`.

**Test**: shuffle the pilot pack's case order, recompute `content_digest`, run `pack check`. Assert it verifies. Add the shuffled variant to `tests/bench.rs`.

### 2.4 Limits are checked where the spec says

**Finding**: `runner.rs:117` reads every asset with `max_input_bytes` before creating the output directory, so an oversized asset aborts the whole run with no rows. `check_experiment` never compares `byte_length` against the limit. `validate_limits` at `runner.rs:257` accepts `max_request_bytes == max_input_bytes`, but hex encoding doubles the candidate, so cases above half the limit are silently `Unavailable` and counted as false negatives while the run reports `complete`.

**Change**:
- `check_experiment` rejects any case with `byte_length > limits.max_input_bytes` at check time, naming the case.
- `check_experiment` encodes every prospective wire request exactly as `execute` will, for every case and every subprocess system, and rejects the experiment naming the first case whose encoded request exceeds `max_request_bytes`. A formula is not enough: the request carries the hex-doubled candidate plus a `TrustedContext` whose `task` string and `permissions` list are unbounded, so no closed-form bound is provable without also imposing limits on those fields. Encoding the real request is exact and costs one serialisation per case at check time, which the scale probe already shows is cheap.
- Factor the request construction out of `execute` into one function both paths call, so check and run cannot disagree.
- `run()` treats an asset that fails the limit at run time as a row-level `Unavailable` with a diagnostic, never an `Err`, per FR-732 and FR-735. After the check-time rejection this is a defensive path, not the expected one.
- `pack::validate_cases` clamps `byte_length` to the 16 MiB ceiling before any read (this is also security finding 3.2).

**Test**: experiment with `max_input_bytes = 1024` over a pack with a 2 KiB asset. Assert `bench experiment` fails naming the case. Second test: a contextual case whose `task` is 900 KiB under `max_request_bytes = 1 MiB`; assert `bench experiment` rejects it naming the case, and that the request bytes the check computed equal the bytes `execute` would send.

### 2.5 Paired analysis has a declared baseline

**Finding**: `report.rs:423` sorts each group by `case_id` and takes adjacent windows, so which transitions exist and their direction depend on lexical id naming. The pilot never reports `aligned_instruction -> non_instruction`.

**Change**: add an optional `baseline_case_id` per group to the pack contract, validated in `pack::check` (must name a member of the group). When absent, enumerate all ordered pairs within the group rather than adjacent ones. Bump `please-bench-pack` schema version.

Counts, so the pilot diff is predictable: a three-member group yields 2 adjacent transitions today. With a declared baseline it still yields 2, both from the baseline, so the total stays at 60 but the pairs change. With no baseline and full enumeration it yields 6 per group, 180 total. The earlier version of this plan said the count would double; it does not.

**Test**: pilot pack with baseline declared; assert 60 transitions, every `case_a` equal to its group's baseline. Rename case ids in a copy; assert the report is unchanged. A pack without baselines; assert 6 per three-member group.

### 2.6 Manifest paths resolve from one base

**Finding**: `runner.rs:71` uses `path.parent().unwrap_or(".")`, but `Path::new("x.json").parent()` is `Some("")`, so `canonicalize("")` fails for a bare filename. Same shape at `pack.rs:81` and `system.rs:101`. `exposure_paths` resolve relative to the pack directory while `pack_path` and `system_paths` resolve relative to the experiment directory, and absolute paths are rejected.

**Change**: one helper `manifest_root(path)` that maps `Some("")` to `"."`. Resolve `exposure_paths` against the experiment directory like their siblings, and allow absolute paths for exposure files since they are run outputs, not pack contents. Document the base in BENCH.md.

**Test**: `bench experiment --manifest bench/contextual-pilot.experiment.json` from `crates/eval` succeeds. An experiment with a non-empty `exposure_paths` against a holdout pack verifies.

### 2.7 Four-way relation matrix is complete

**Finding**: only non-zero cells are emitted; pilot shows 3 rows where SC-706 asks for the full matrix.

**Change**: emit all 16 cells with zeros.

**Test**: assert 16 cells per system per stratum in the pilot report.

## Phase 4 — The bench joins the eval crate (two to three days)

These are the architecture review's three strong candidates and one worth-exploring candidate. Order matters: 4.1 first, because 4.2 and 4.3 become mechanical after it.

### 4.1 One saved-run module (cleanup, not a measurement blocker)

`bench/runner.rs:487-539` and `run.rs:90-137, 393-455` both implement "a run directory whose completion record carries a digest and row count, verified before any report". The first version of this plan claimed the bench wrote in place and could leave a torn manifest. That was wrong: `write_manifest` at `runner.rs:487` writes a `.pending` file, syncs it, and renames. The two differ only in detail: `run::atomic_write` opens with `create_new` and syncs the directory afterwards; the bench does neither. Neither difference corrupts a run.

So this is duplication, not a defect. Extract `eval::saved_run::SavedRun<Row>` owning publication, completion record, digest verification, and unverified-run detection, and let both `run` and `bench` call it. The bench picks up `create_new` and the directory sync as a side effect. Fold `bench/report.rs` `MetricCounts` and `RelationMatrix` onto `metrics.rs` `Tally` and `SliceMetrics`.

**Test**: existing `run.rs` and `bench` tests pass against the shared module; one new test asserts both callers refuse to publish over an existing `.pending` file.

### 4.2 Bench adapter uses the product runtime

Done in 2.2.

### 4.3 One identity module

Promote `bench/identity.rs` to `eval::identity` and delete the five re-typings at `run.rs:424`, `manifest.rs:74`, `capture.rs:70-76`, `replay.rs:274`, `boundary.rs:59`, plus the hex checks at `models.rs:221` and `capture.rs:74`. The bench version is the only one with hex validation, path safety, and bounded reads; after this step that hardening applies everywhere.

**Test**: every existing digest test passes unchanged; grep for `Sha256::new()` outside `identity.rs` returns nothing.

### 4.4 Fold shallow bench modules

Move the types in `bench/adapter.rs`, `bench/protocol.rs`, `bench/exposure.rs` into `bench/model.rs`. Keep `please.rs` and `process.rs` as the two adapters behind the execution seam. Delete dead code the review named: `runner::write_json`, `CoverageState::as_str`, `_system_digest`, `VerifiedSystem.root`, `VerifiedPack.taxonomy`.

### 4.5 Move gate and selection out of the eval binary

`main.rs:1104-1243` (`check_gate`, `select`, `write_report`) is untested wiring around tested pure functions. Move the bodies into `metrics` and `run` as functions taking paths and returning values. Leave `main.rs` as argument parsing and exit codes.

**Test**: unit tests for `check_gate` covering the incomplete-run, unverified-run, and below-baseline cases the CONTEXT.md agreed behavior names.

### 4.6 Give `bench/mod.rs` a navigational header

The same module table `eval/src/lib.rs:1-50` has: what lives in each file, what it must not do. Zero-comment files in the riskiest code is the inverse of where the prose should be.
